## 1. Design it before you build it

*About 1 hour*

Data engineers draw the pipeline before writing code. A drawing shows the gaps: where data comes from, where it is stored, what checks it, and what runs when. This project uses the [medallion pattern](https://thejoinery.dev/#/glossary/term/medallion): three layers, each with one job.

| Layer | Also called | Its one job | Built with |
|---|---|---|---|
| Raw | bronze | Keep exactly what arrived, plus where and when it came from | Python (ingest.py) |
| Staging | silver | Clean and type it, remove duplicates, keep the latest version, set bad rows aside | dbt |
| Marts | gold | Shape it for people: a star schema and a daily KPI table | dbt |

Draw your own version first, with boxes for each layer and arrows for each step. [Excalidraw](https://excalidraw.com/) and [draw.io](https://app.diagrams.net/) are free and work in the browser. Then compare with this one:

## 3. Read the source and write a contract

*About 1 hour*

Unzip **batch 1** into your `just-now-pipeline` folder. It creates `landing/` with three folders: `reference/` (customers, sellers, products), `orders/` and `order_items/`, one file per day.

Open a few order files. The important thing to notice: **an order appears more than once**. A new row arrives every time its status changes. Here is one order across three files:

| order_id | order_status | updated_at | file |
|---|---|---|---|
| O001949 | processing | 2025-10-14 21:51:51 | orders_2025-10-14.csv |
| O001949 | shipped | 2025-10-16 11:04:39 | orders_2025-10-16.csv |
| O001949 | delivered | 2025-10-19 05:41:46 | orders_2025-10-19.csv |

So the source sends **changes**, not a finished table. Your pipeline has to keep the latest version of each order: a simple form of [change data capture](https://thejoinery.dev/#/glossary/term/change-data-capture).

Now write `CONTRACT.md`: a short [data contract](https://thejoinery.dev/#/glossary/term/data-contract) that says what the feed promises. For each file: the columns, their types and rules, when it arrives, and what happens when a rule is broken.

<details>
<summary>Show a model contract</summary>


**Owner:** Orders system team. **Consumer:** Data team (this pipeline).
**Arrives:** one pair of files per day in `landing/orders/` and `landing/order_items/`, by 05:00, for the previous day. Files can arrive late; a late file must still be loaded.

### orders_YYYY-MM-DD.csv: one row per order per status change
| column | type | rules |
|---|---|---|
| order_id | text | required; the same order appears once per status change |
| customer_id | text | required; must exist in `reference/customers.csv` |
| order_status | text | one of processing, shipped, delivered, cancelled, returned |
| order_purchase_ts | timestamp | required; the same on every version of an order |
| updated_at | timestamp | required; when this status change happened. The latest one wins |
| order_estimated_delivery_date | date | required |
| order_delivered_ts | timestamp | empty until the order is delivered |
| delivery_method | text | added from 2025-11-15: standard, express or collect. Empty before that |

### order_items_YYYY-MM-DD.csv: one row per item, sent once, on the day the order is placed
| column | type | rules |
|---|---|---|
| order_id | text | required; matches an order |
| order_item_id | integer | 1, 2, 3 … within an order; (order_id, order_item_id) is unique |
| product_id | text | must exist in `reference/products.csv` |
| seller_id | text | required |
| price | decimal | rand, 0 or more |
| freight_value | decimal | rand, 0 or more |

### What happens when the rules are broken
- A row that breaks a rule is moved to quarantine with a reason, and the rest of the file still loads.
- If more than 1% of rows are quarantined, the pipeline stops and nobody gets that morning's numbers until someone checks.
- New columns are added to the raw layer automatically, and the data team is told (the ingest log says so).

## 4. Ingest the raw files, with Python

*About 2 hours*

Write `ingest.py`. It moves new files from `landing/` into a DuckDB file, `warehouse/just_now.duckdb`, in a schema called `raw`. The rules:

1. **Raw means raw.** Store every column as text, exactly as it arrived. Cleaning comes later.
2. **Stamp every row** with `_source_file` (the file name) and `_loaded_at` (the time you loaded it).
3. **Load each file once.** Keep a table, `raw.ingested_files`, of what has been loaded, and skip those next time.
4. **One transaction per file**, so a crash halfway through a file leaves nothing half-loaded.
5. **Reference files** (customers, sellers, products) are a full snapshot: replace those tables each run.

> **Tip:** DuckDB reads a CSV with `read_csv('path', all_varchar = true)`. To add rows by column name rather than position, use `INSERT INTO raw.orders BY NAME SELECT ...`. That matters in step 9. Related: [incremental load](https://thejoinery.dev/#/glossary/term/incremental-load).

<details>
<summary>Show the model script</summary>

```python ingest.py
"""Ingest: copy new files from landing/ into the raw layer of the warehouse (warehouse/just_now.duckdb).

Run it from the project folder:  python ingest.py

Rules this script follows (each one is a real data engineering habit):
  - Raw means raw. Every column is stored as text, exactly as it arrived. Cleaning happens later, in dbt.
  - Every row is stamped with the file it came from (_source_file) and when it was loaded (_loaded_at).
  - A file is only loaded once. raw.ingested_files remembers what has been loaded, so running this
    twice changes nothing (it is idempotent).
  - If a file brings a column the table has never seen, the column is added instead of crashing.
  - Each file loads in its own transaction: if one fails halfway, nothing from it is kept.
"""
from pathlib import Path
import duckdb

LANDING = Path("landing")
WAREHOUSE = Path("warehouse") / "just_now.duckdb"
DAILY_TABLES = ["orders", "order_items"]           # landing/orders/*.csv -> raw.orders, and so on
REFERENCE = ["customers", "sellers", "products"]   # landing/reference/*.csv, replaced in full each run


def connect():
    WAREHOUSE.parent.mkdir(exist_ok=True)
    con = duckdb.connect(str(WAREHOUSE))
    con.execute("CREATE SCHEMA IF NOT EXISTS raw")
    con.execute("""CREATE TABLE IF NOT EXISTS raw.ingested_files (
        file_name VARCHAR PRIMARY KEY, table_name VARCHAR, row_count INTEGER, loaded_at TIMESTAMP)""")
    return con


def read_file(con, path):
    """Read one CSV with every column as text, plus the two stamp columns."""
    return f"""SELECT *, '{path.name}' AS _source_file, current_timestamp AS _loaded_at
               FROM read_csv('{path.as_posix()}', all_varchar = true, header = true)"""


def table_exists(con, table):
    return con.execute("SELECT COUNT(*) FROM information_schema.tables WHERE table_schema = 'raw' AND table_name = ?", [table]).fetchone()[0] > 0


def add_new_columns(con, table, path):
    """Schema drift: if the file has columns the table does not, add them (as text)."""
    file_cols = [r[0] for r in con.execute(f"DESCRIBE {read_file(con, path)}").fetchall()]
    table_cols = {r[0] for r in con.execute(f"DESCRIBE raw.{table}").fetchall()}
    for col in file_cols:
        if col not in table_cols:
            con.execute(f'ALTER TABLE raw.{table} ADD COLUMN "{col}" VARCHAR')
            print(f"  new column found in {path.name}: {col} (added to raw.{table})")


def load_daily(con, table):
    done = {r[0] for r in con.execute("SELECT file_name FROM raw.ingested_files WHERE table_name = ?", [table]).fetchall()}
    files = sorted((LANDING / table).glob(f"{table}_*.csv"))
    new = [f for f in files if f.name not in done]
    for path in new:
        con.execute("BEGIN TRANSACTION")
        try:
            if not table_exists(con, table):
                con.execute(f"CREATE TABLE raw.{table} AS {read_file(con, path)} LIMIT 0")
            add_new_columns(con, table, path)
            before = con.execute(f"SELECT COUNT(*) FROM raw.{table}").fetchone()[0]
            con.execute(f"INSERT INTO raw.{table} BY NAME {read_file(con, path)}")   # BY NAME: match columns by name, not position
            rows = con.execute(f"SELECT COUNT(*) FROM raw.{table}").fetchone()[0] - before
            con.execute("INSERT INTO raw.ingested_files VALUES (?, ?, ?, current_timestamp)", [path.name, table, rows])
            con.execute("COMMIT")
        except Exception:
            con.execute("ROLLBACK")
            raise
    print(f"raw.{table:12s} {len(new):3d} new files, {len(files) - len(new):3d} already loaded")
    return len(new)


def load_reference(con):
    for name in REFERENCE:
        path = LANDING / "reference" / f"{name}.csv"
        if path.exists():
            con.execute(f"CREATE OR REPLACE TABLE raw.{name} AS {read_file(con, path)}")
            n = con.execute(f"SELECT COUNT(*) FROM raw.{name}").fetchone()[0]
            print(f"raw.{name:12s} {n:,} rows (full snapshot)")


def main():
    con = connect()
    try:
        load_reference(con)
        new_files = sum(load_daily(con, t) for t in DAILY_TABLES)
    finally:
        con.close()
    return new_files


if __name__ == "__main__":
    main()
```

</details>

> **You should see:** the first run loads 31 order files and 31 item files. Run it again straight away: it says **0 new files, 31 already loaded**, and the row counts do not change. That is idempotency, proved.

## 5. Clean it in the staging layer, with dbt

*About 2 to 3 hours*

dbt turns SQL `SELECT` statements into tables and views, in the right order, and tests them. Each model is one `.sql` file. `{{ source(...) }}` points at a raw table, and `{{ ref(...) }}` points at another model, which is how dbt knows the order to build things in.

Set up the project. These are short, so here they are in full:

```yaml transform/dbt_project.yml
name: just_now
version: "1.0.0"
profile: just_now

model-paths: ["models"]
test-paths: ["tests"]

models:
  just_now:
    staging:
      +materialized: view
      +schema: staging
    marts:
      +materialized: table
      +schema: marts
```

```yaml transform/profiles.yml
# Where dbt builds the models. run_pipeline.py sets JUST_NOW_DB to the full path.
# If you run dbt yourself from inside the transform folder, the default below is used.
just_now:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: "{{ env_var('JUST_NOW_DB', '../warehouse/just_now.duckdb') }}"
      threads: 4
```

```sql transform/macros/generate_schema_name.sql
-- Use the folder's schema name as it is (staging, marts), instead of dbt's default of "main_staging".
{% macro generate_schema_name(custom_schema_name, node) -%}
  {{ custom_schema_name if custom_schema_name else target.schema }}
{%- endmacro %}
```

Then write `models/staging/sources.yml` to describe the raw tables, and these models:

- `stg_customers`, `stg_products`, `stg_sellers`: rename and cast types.
- `stg_order_versions`: every version of every order, typed, with exact duplicate rows removed.
- `stg_orders`: **one row per order, its latest version**.
- `stg_order_items`: typed, one row per order and item number.

> **Tip:** For the latest version, number each order's rows from newest to oldest and keep number 1: `QUALIFY row_number() OVER (PARTITION BY order_id ORDER BY updated_at DESC) = 1`. See [window functions](https://thejoinery.dev/#/glossary/term/window-function) and [deduplication](https://thejoinery.dev/#/glossary/term/deduplication).

Run it from the `transform` folder with `dbt build --profiles-dir .`

```sql models/staging/stg_order_versions.sql
-- Every version of every order, typed and tidied.
-- Exact duplicate rows (the same file content twice) are removed.
-- Rows that break the rules are NOT dropped silently: they go to quarantine_order_versions instead.
with typed as (
    select distinct
        order_id,
        nullif(trim(customer_id), '')                       as customer_id,
        lower(trim(order_status))                           as order_status,
        cast(order_purchase_ts as timestamp)                as order_purchase_ts,
        cast(updated_at as timestamp)                       as updated_at,
        cast(order_estimated_delivery_date as date)         as promised_date,
        cast(nullif(order_delivered_ts, '') as timestamp)   as delivered_ts,
        {{ column_or_null(source('raw', 'orders'), 'delivery_method') }},  -- only in files from 2025-11-15 onwards
        _source_file,
        _loaded_at
    from {{ source('raw', 'orders') }}
)
select *
from typed
where customer_id is not null
  and order_status in ('processing', 'shipped', 'delivered', 'cancelled', 'returned')
```

```sql models/staging/stg_orders.sql
-- One row per order: its LATEST version. A status change arrives as a new row, so the newest one wins.
-- Ties (the same timestamp loaded twice) are broken by load time.
select *
from {{ ref('stg_order_versions') }}
qualify row_number() over (partition by order_id order by updated_at desc, _loaded_at desc) = 1
```

```sql models/staging/stg_order_items.sql
select
    order_id,
    cast(order_item_id as integer)          as order_item_id,
    product_id,
    seller_id,
    cast(price as decimal(10, 2))           as price,
    cast(freight_value as decimal(10, 2))   as freight_value,
    _source_file,
    _loaded_at
from {{ source('raw', 'order_items') }}
qualify row_number() over (partition by order_id, order_item_id order by _loaded_at desc) = 1
```

```sql models/staging/stg_customers.sql
select
    customer_id,
    customer_city,
    customer_province,
    cast(signup_date as date) as signup_date
from {{ source('raw', 'customers') }}
```

Your `stg_order_versions` will be simpler than this one for now: the quarantine filter and the `column_or_null` macro come in step 9.

## 6. Build the fact table incrementally

*About 2 hours*

`fct_orders` has one row per order: its latest status, item count, revenue, delivery dates and whether it was late. With three months of data you could rebuild it from scratch every time. With three years you could not. So build it as an **incremental** model: after the first run, only rebuild orders that changed.

The tricky part is deciding what **changed** means. Two traps:

1. **Filter on when you received the data (`_loaded_at`), not when it happened (`updated_at`).** A late file is full of old `updated_at` values. Filter on `updated_at` and you skip the late file forever.
2. **An order also changes when its items arrive.** If an item file is late, the order is already in `fct_orders` with no items, and needs rebuilding when they turn up.

> **Tip:** In dbt, `{{ config(materialized='incremental', unique_key='order_id', incremental_strategy='delete+insert') }}` replaces the rows for changed orders. Inside `{% if is_incremental() %}`, `{{ this }}` is the existing table, so `max(_loaded_at)` from it is the last time you ran.

<details>
<summary>Show the model fct_orders</summary>

```sql models/marts/fct_orders.sql
-- The fact table: one row per order, with its latest status and its items added up.
-- Incremental: after the first run, only orders that changed since the last run are rebuilt.
--
-- "Changed" uses _loaded_at (when WE received the data), not updated_at (when it happened).
-- A late file is full of old updated_at values, so filtering on updated_at would skip it forever.
-- An order also counts as changed when its items arrive later than the order itself.
{{ config(materialized='incremental', unique_key='order_id', incremental_strategy='delete+insert') }}
-- depends_on: {{ ref('stg_order_versions') }}
-- (tells dbt about a ref that only appears inside the is_incremental() block below)

with changed as (
    {% if is_incremental() %}
    select order_id from {{ ref('stg_order_versions') }} where _loaded_at > (select max(_loaded_at) from {{ this }})
    union
    select order_id from {{ ref('stg_order_items') }}    where _loaded_at > (select max(_loaded_at) from {{ this }})
    {% else %}
    select order_id from {{ ref('stg_orders') }}
    {% endif %}
),
items as (
    select
        order_id,
        count(*)            as item_count,
        sum(price)          as revenue,
        sum(freight_value)  as freight,
        max(_loaded_at)     as items_loaded_at
    from {{ ref('stg_order_items') }}
    where order_id in (select order_id from changed)
    group by order_id
)
select
    o.order_id,
    o.customer_id,
    cast(o.order_purchase_ts as date)                       as order_date,
    o.order_status,
    o.delivery_method,
    coalesce(i.item_count, 0)                               as item_count,
    i.revenue,
    i.freight,
    i.order_id is null                                      as items_missing,   -- the items file has not arrived yet
    o.promised_date,
    cast(o.delivered_ts as date)                            as delivered_date,
    case when o.delivered_ts is null then null
         else cast(o.delivered_ts as date) > o.promised_date end as is_late,
    date_diff('hour', o.order_purchase_ts, o.delivered_ts) / 24.0 as days_to_deliver,
    o.updated_at,
    greatest(o._loaded_at, coalesce(i.items_loaded_at, o._loaded_at)) as _loaded_at
from {{ ref('stg_orders') }} o
left join items i using (order_id)
where o.order_id in (select order_id from changed)
```

The `-- depends_on:` line is there because dbt cannot see a `ref()` that is inside an `if` block. Without it, the second run fails with a compilation error, which is exactly what happened when this pipeline was first built.

</details>

> **You should see:** the most important check in this project. Copy your warehouse file, then run `dbt build --full-refresh` on the copy, which rebuilds everything from scratch. The incremental `fct_orders` and the full-refresh one must be **identical**. When this project was tested, after all three batches both had 15 056 rows and matched exactly.

## 7. Build the business-ready layer

*About 1 hour*

Add the rest of the [star schema](https://thejoinery.dev/#/glossary/term/star-schema), and the table the morning dashboard will read:

- `dim_customer`: one row per customer.
- `dim_date`: one row per day from 1 October to 31 December 2025.
- `kpi_daily`: one row per day with orders, revenue, cancellations, deliveries, late % and average days to deliver. Add a column for orders still missing their items, so nobody mistakes an incomplete day for a bad day.

<details>
<summary>Show the model marts</summary>

```sql models/marts/kpi_daily.sql
-- The table the morning dashboard reads: one row per day.
select
    f.order_date                                                         as date,
    count(*)                                                             as orders,
    sum(f.revenue) filter (where f.order_status <> 'cancelled')          as revenue,
    count(*) filter (where f.order_status = 'cancelled')                 as cancelled,
    count(*) filter (where f.order_status in ('delivered', 'returned'))  as delivered,
    round(100.0 * avg(case when f.is_late then 1 else 0 end) filter (where f.is_late is not null), 1) as late_pct,
    round(avg(f.days_to_deliver), 2)                                     as avg_days_to_deliver,
    count(*) filter (where f.items_missing)                              as orders_missing_items
from {{ ref('fct_orders') }} f
group by f.order_date
order by f.order_date
```

```sql models/marts/dim_date.sql
select
    cast(d as date)              as date,
    year(d)                      as year,
    month(d)                     as month,
    strftime(d, '%Y-%m')         as year_month,
    dayname(d)                   as day_name,
    isodow(d) in (6, 7)          as is_weekend
from range(date '2025-10-01', date '2026-01-01', interval 1 day) as t(d)
```

</details>

## 8. Add data quality tests

*About 1 to 2 hours*

Tests are how the pipeline knows the data is wrong before a person does. In dbt there are two kinds, and `dbt build` runs each test straight after the model it checks. See [data quality](https://thejoinery.dev/#/glossary/term/data-quality).

- **Generic tests** in `models/schema.yml`: `unique`, `not_null`, `accepted_values` and `relationships`, one line each.
- **Singular tests**: a `.sql` file in `tests/` that selects the bad rows. The test fails if it returns any.

Write tests that check: order IDs are unique and present; every order has a customer who exists; the status is one of the five allowed values; revenue is never negative; nothing is delivered before it was ordered; and each day appears once in `kpi_daily`.

<details>
<summary>Show the model tests</summary>

```yaml models/schema.yml
version: 2

models:
  - name: stg_orders
    description: One row per order, its latest status.
    columns:
      - name: order_id
        data_tests: [unique, not_null]
      - name: customer_id
        data_tests:
          - not_null
          - relationships:
              arguments: {to: ref('stg_customers'), field: customer_id}
      - name: order_status
        data_tests:
          - accepted_values:
              arguments: {values: ['processing', 'shipped', 'delivered', 'cancelled', 'returned']}

  - name: stg_customers
    columns:
      - name: customer_id
        data_tests: [unique, not_null]

  - name: stg_order_items
    columns:
      - name: product_id

              arguments: {to: ref('stg_products'), field: product_id}

    description: The fact table. One row per order.
    columns:
      - name: order_id

        data_tests: [not_null]

  - name: kpi_daily

      - name: date

```

## 9. Handle change: new columns, late files and bad data

*About 2 to 3 hours*

Real feeds change without warning. Load the next batches one at a time and fix what breaks.

### Batch 2: a column appears

Unzip **batch 2** into the project folder and run `python ingest.py`. From 15 November the orders files have a new column, `delivery_method`. If your ingest inserts by position, it now fails or puts values in the wrong columns. Make it compare each file's columns with the table, and add any new ones before inserting.

Now there is a second problem. Your staging model should select `delivery_method`, but if anyone rebuilds from batch 1 only, the column does not exist yet and the model breaks. A small dbt macro solves it: use the column if the table has it, and an empty column if not.

```sql macros/column_or_null.sql
-- Schema drift: use a column if the table has it, otherwise an empty (NULL) column with the same name.
-- This lets a model run on data from before AND after a source starts sending a new column.
{% macro column_or_null(relation, column) -%}
  {%- set existing = adapter.get_columns_in_relation(relation) | map(attribute='name') | map('lower') | list -%}
  {%- if column | lower in existing -%}
    {{ column }}
  {%- else -%}
    cast(null as varchar) as {{ column }}
  {%- endif -%}
{%- endmacro %}
```

Use it in `stg_order_versions` as `{{ column_or_null(source('raw', 'orders'), 'delivery_method') }}`.

Also look at 3 November. That day's files are missing from batch 2, but later files still contain status updates for orders placed that day. So those orders appear in `fct_orders` with **no items and no revenue**. That is why `items_missing` exists: `kpi_daily` shows those orders are incomplete instead of reporting a terrible day.

### Batch 3: the late file and the bad file

Unzip **batch 3** and run `dbt build`. Two things happen. The 3 November files finally arrive, and because your incremental model looks at `_loaded_at`, those orders are rebuilt with their items, revenue and all. And this time the build fails:

```text dbt build output
11 of 25 FAIL 1 accepted_values_stg_orders_order_status__processing__shipped__delivered__cancelled__returned  [FAIL 1 in 0.12s]
12 of 25 FAIL 3 not_null_stg_orders_customer_id  ... [FAIL 3 in 0.15s]

The pipeline stopped: these checks failed: accepted_values_stg_orders_order_status..., not_null_stg_orders_customer_id
```

The 12 December orders file is bad: some rows have no customer, some say `delivred`, and some rows appear twice. **This is the pipeline working**: it refused to publish numbers built on bad data.

Now fix it properly. Do not delete the bad rows silently. Move them to a **quarantine** model with a reason, filter them out of staging, and add a test that stops everything if too many rows are quarantined, because that means something bigger is wrong.

<details>
<summary>Show the model quarantine</summary>

```sql models/staging/quarantine_order_versions.sql
-- Rows that failed the rules in stg_order_versions, kept so someone can look at them and fix the source.
select
    *,
    case
        when nullif(trim(customer_id), '') is null then 'missing customer_id'
        else 'unknown status: ' || coalesce(order_status, '(empty)')
    end as reason
from {{ source('raw', 'orders') }}
where nullif(trim(customer_id), '') is null
   or lower(trim(order_status)) not in ('processing', 'shipped', 'delivered', 'cancelled', 'returned')
```

```sql tests/assert_quarantine_is_small.sql
-- Quarantine is for the odd bad row. If more than 1% of order rows are quarantined,
-- something bigger is wrong with the source, and the pipeline should stop.
select count(*) as quarantined
from {{ ref('quarantine_order_versions') }}
having count(*) > 0.01 * (select count(*) from {{ source('raw', 'orders') }})
```

And the end of `stg_order_versions` keeps only the good rows:

```sql models/staging/stg_order_versions.sql
-- Every version of every order, typed and tidied.
-- Exact duplicate rows (the same file content twice) are removed.
-- Rows that break the rules are NOT dropped silently: they go to quarantine_order_versions instead.
with typed as (
    select distinct
        order_id,
        nullif(trim(customer_id), '')                       as customer_id,
        lower(trim(order_status))                           as order_status,
        cast(order_purchase_ts as timestamp)                as order_purchase_ts,
        cast(updated_at as timestamp)                       as updated_at,
        cast(order_estimated_delivery_date as date)         as promised_date,
        cast(nullif(order_delivered_ts, '') as timestamp)   as delivered_ts,
        {{ column_or_null(source('raw', 'orders'), 'delivery_method') }},  -- only in files from 2025-11-15 onwards
        _source_file,
        _loaded_at
    from {{ source('raw', 'orders') }}
)
select *
from typed
where customer_id is not null
  and order_status in ('processing', 'shipped', 'delivered', 'cancelled', 'returned')
```

</details>

> **You should see:** every test passes again, and the quarantine holds 25 rows: 14 with a missing customer and 11 with an unknown status. Exact duplicates were removed in staging, so they never reach the quarantine.

## 10. Orchestrate and schedule it

*About 1 to 2 hours*

Write `run_pipeline.py` to run everything in order with one command: ingest, then `dbt build`, then a freshness check. It records every run, successful or not, in a table called `ops.run_log`, and **exits with an error** if anything fails. That error is how a scheduler knows a run went wrong. See [orchestration](https://thejoinery.dev/#/glossary/term/orchestration).

<details>
<summary>Show the model script</summary>

```python run_pipeline.py
"""Run the whole pipeline with one command:  python run_pipeline.py

  1. ingest      new files in landing/ -> raw tables
  2. dbt build   staging and marts models, with every data test straight after its model
  3. freshness   warn if the raw data is getting old
  4. run log     one row in ops.run_log for every run, whether it worked or not

If any data test fails, dbt stops building anything that depends on it, this script records
the failure and exits with an error code. That is what makes a scheduler (GitHub Actions) mark the run red.
"""
import os, sys, time
from datetime import datetime, timezone
from pathlib import Path
import duckdb
from dbt.cli.main import dbtRunner

import ingest

ROOT = Path(__file__).parent.resolve()
DB = ROOT / "warehouse" / "just_now.duckdb"
DBT_ARGS = ["--project-dir", str(ROOT / "transform"), "--profiles-dir", str(ROOT / "transform")]


def log_run(started, status, files, message):
    con = duckdb.connect(str(DB))
    con.execute("CREATE SCHEMA IF NOT EXISTS ops")
    con.execute("""CREATE TABLE IF NOT EXISTS ops.run_log (
        started_at TIMESTAMP, finished_at TIMESTAMP, status VARCHAR, new_files INTEGER, message VARCHAR)""")
    con.execute("INSERT INTO ops.run_log VALUES (?, ?, ?, ?, ?)",
                [started, datetime.now(timezone.utc).replace(tzinfo=None), status, files, message])
    con.close()


def main():
    os.environ["JUST_NOW_DB"] = str(DB)
    os.chdir(ROOT)
    started = datetime.now(timezone.utc).replace(tzinfo=None)
    t = time.time()

    print("===== 1. ingest =====")
    try:
        files = ingest.main()
    except Exception as e:
        log_run(started, "failed", 0, f"ingest: {e}")
        print(f"\nThe pipeline stopped at ingest: {e}")
        sys.exit(1)

    print("\n===== 2. dbt build (models and tests) =====")
    result = dbtRunner().invoke(["build", *DBT_ARGS])
    if not result.success:
        failed = [r.node.name for r in (result.result or []) if str(r.status) in ("fail", "error")]
        log_run(started, "failed", files, "dbt build: " + ", ".join(failed))
        print("\nThe pipeline stopped: these checks failed:", ", ".join(failed) or "see the dbt output above")
        sys.exit(1)

    print("\n===== 3. source freshness =====")
    dbtRunner().invoke(["source", "freshness", *DBT_ARGS])   # warnings only: never stops the run

    log_run(started, "success", files, "ok")
    print(f"\nAll done in {time.time() - t:.0f} seconds. {files} new files loaded.")


if __name__ == "__main__":
    main()
```

</details>

Now make it run by itself every morning, with **GitHub Actions**:

1. Create a new **public** repository on GitHub called `just-now-pipeline`.
2. Add the workflow file below at `.github/workflows/pipeline.yml`.
3. Commit everything, including `landing/`, and push it: `git add .`, `git commit -m "First pipeline"`, then follow GitHub's instructions to push.
4. On GitHub, open the **Actions** tab, choose **Morning pipeline**, and select **Run workflow** to try it straight away.

```yaml .github/workflows/pipeline.yml
# Runs the pipeline every morning at 06:00 South African time (04:00 UTC), and whenever you press
# "Run workflow" on the Actions tab. Free for public repositories.
name: Morning pipeline

on:
  schedule:
    - cron: "0 4 * * *"
  workflow_dispatch:

jobs:
  run:
    runs-on: ubuntu-latest
    steps:
      - name: Get the code and the landing files
        uses: actions/checkout@v6

      - name: Set up Python
        uses: actions/setup-python@v6
        with:
          python-version: "3.12"

      - name: Install the tools
        run: pip install -r requirements.txt

      - name: Run the pipeline
        run: python run_pipeline.py

      - name: Keep the warehouse and dbt's report for 7 days
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: pipeline-output
          path: |
            warehouse/just_now.duckdb
            transform/target/run_results.json
          retention-days: 7
```

- [GitHub Actions documentation](https://docs.github.com/en/actions): Official guide, including how schedules work.

> **Tip:** GitHub runs a scheduled workflow in UTC, and the time is not exact: busy periods can delay it by several minutes. In this setup GitHub starts with an empty warehouse each time and rebuilds it from the files in `landing/`. That is only safe because your pipeline is idempotent, and step 6 proved the incremental result equals a full rebuild.

> **You should see:** a green tick on the Actions tab. Open the run to read each step's output, and download **pipeline-output** to get the warehouse file it built.

## 11. Watch it: run log, freshness and lineage

*About 1 hour*

A pipeline nobody watches fails quietly. Three habits:

- **The run log.** `SELECT * FROM ops.run_log ORDER BY started_at DESC` shows every run, how many new files it loaded, and whether it failed.
- **Freshness.** `sources.yml` says the raw data should be less than a day old. `dbt source freshness` warns when it is not. See [data freshness](https://thejoinery.dev/#/glossary/term/data-freshness).
- **Lineage.** Run `dbt docs generate --profiles-dir .`, then `dbt docs serve --profiles-dir .`, and open the graph: it draws every model and what it depends on. When a number looks wrong, this shows where to look. See [data lineage](https://thejoinery.dev/#/glossary/term/data-lineage).

> **You should see:** after loading the three batches one at a time, the run log holds one successful row per batch (if you ran a batch twice, the second shows 0 new files), and the lineage graph shows the raw tables flowing into staging and then the marts.

## 12. Why it matters, and how to talk about it

*About 30 minutes*

| What you built | What it protects in a real company |
|---|---|
| Raw layer that keeps everything, stamped | You can always replay history, and prove where any number came from |
| Idempotent loads | Reruns after a failure are safe: no double-counted revenue |
| Incremental model on load time | Late files are not lost, and runs stay fast as data grows |
| Tests that stop the build | Wrong numbers never reach the morning meeting |
| Quarantine with reasons | One bad row does not block the business, and someone can fix the source |
| Scheduled runs and a run log | Nobody has to remember to press a button, and failures are visible |

### Say it in an interview

- "I built a pipeline that loads daily order files into a raw layer, cleans them in dbt, and publishes a star schema and a daily KPI table every morning on GitHub Actions."
- "The source sends a new row every time an order's status changes, so staging keeps the latest version with a window function."
- "The fact table is incremental, and it picks up changes by load time, not event time. That way a file that arrives two days late is still processed. I proved it by comparing the incremental table with a full rebuild: they were identical."
- "When a bad file arrived, the tests failed and the pipeline stopped before anyone saw wrong numbers. I added a quarantine so bad rows are set aside with a reason and the rest of the data still flows."

## 13. Take it further

*As long as you like*

- **Move it to the cloud.** Swap DuckDB for Snowflake (it has a free trial) by installing `dbt-snowflake` and changing `profiles.yml`. The models barely change, and that is the point of dbt.
- **Keep history of customers.** If a customer moves province, the old value disappears. Add a dbt snapshot to track changes over time: a [slowly changing dimension](https://thejoinery.dev/#/glossary/term/scd).
- **Get told when it fails.** GitHub can email you when a workflow fails. Turn it on in your notification settings.
- **Try a real orchestrator.** Rebuild the schedule in Dagster or Airflow, which add retries, backfills and a visual run history.
- **Store files as Parquet,** partitioned by date, and compare the speed and size with CSV.
